# A green deployment and a failed user request

`VW-C001` · beginner · 25 minutes · draft · free/offline

## Question

Simulation: checkout release R42 passes the configured pipeline tests and its processes are running. A gateway sample contains 100 checkout requests in five minutes; 18 return 503 and 82 return 200. Response bodies and retries have not been checked. A teammate says, “Delivery succeeded, so operations owns this.”

A **pipeline** is an automated sequence of checks and delivery steps. A **process** is a running program. A **gateway** receives and routes requests. HTTP status 503 indicates that the responding component reports the service unavailable; it does not identify the failed component. No programming experience or external account is needed.

## Task

Answer these original practice questions before opening the solution:

1. What exactly do the successful pipeline and running-process observations establish? Give one limitation of each.
2. What fraction of the gateway sample returned 200? Why is it incorrect to describe that fraction as the percentage of users who successfully checked out?
3. Rewrite “release succeeded” as a measurable user outcome, including the population, correctness, time window and an explicit treatment of missing evidence.
4. Separate one observation, one hypothesis and one bounded decision. What evidence would distinguish a release-specific problem from a shared gateway problem?
5. Assign a coordinator and check owner by role. Explain shared responsibility without allowing multiple people to make unrecorded changes at once.
6. Compare an extra manual approval with an extra user-path check. Under what conditions could either improve the decision, and why does neither automatically make the system reliable?

## Verification

A defensible answer preserves the supplied denominator, does not convert requests into people, distinguishes response status from correct checkout completion and avoids declaring root cause. A proposed check must include a prediction, not just “look at logs.” Explain who acts and what observation would change the decision.

There is no executable lab or setup requirement. This is conceptual practice. Use the [foundations explanation](../foundations/engineering-evidence/README.md) if you need worked definitions.

## Reflection

What could happen before a request reaches the gateway? How could retries make 100 requests represent fewer than 100 people? Why might a rollback restore code without reversing a failed payment attempt?
