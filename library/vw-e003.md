# Review a CI gate before giving it authority

`VW-E003` · intermediate · 40 minutes · draft · free/local

## Mission

A pull request adds a build gate. Review it offline before allowing it into a repository.

## Outcomes

Identify permissions, trust boundaries and missing quality evidence.

## Environment and scope

Text editor only; do not install this intentionally flawed simulation as a workflow.

## Prerequisite checks

Know pull requests, shell exit codes and GitHub Actions job structure.

## Setup

Review this fixture:

```yaml
name: candidate
on: pull_request_target
permissions: write-all
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.event.pull_request.head.sha }}
      - run: bash contributor-check.sh || true
```

## Concepts

An untrusted script inherits its execution context. Suppressing failures makes the gate decorative. Trigger choice controls the trust boundary.

## Tasks

Annotate three risks. Design a replacement using `pull_request`, read-only contents permission, a reviewed immutable checkout action reference, a timeout, and a fixed repository-owned validation command. Explain how a linter, unit tests and an image scan provide different evidence.

## Expected observations

Checking out contributor code in a privileged event is the central hazard; pinning checkout alone does not fix it.

## Verification

Review the replacement against a fork PR, an intentionally failing check and the absence of secrets. Use static review only unless running in a disposable test repository.

## Troubleshooting

If the gate reports green after a failure, remove unconditional success suppression and inspect step exit behavior.

## Cleanup

Keep the fixture outside `.github/workflows`; delete any disposable test repository resources you created.

## Reflection

Which checks should block merges, and who owns exceptions?
